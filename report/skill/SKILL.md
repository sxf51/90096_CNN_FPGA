# Exploratory Experiment Engineering

English edition of the `experiment-exploration` skill; keep the two in sync.

This approach comes from the SRCNN FPGA optimization in `~/School/Hardware/remote/90096_CNN_FPGA`: 170+ experiments, each traceable to its experiment card, raw reports, and commit. Scripts and templates live in this skill's directory (`scripts/`, `templates/`).

Division of labor with other skills:

- This skill covers the phase where you don't yet know which approach works. Experiment code lives on experiment branches and in independent copies, never on the mainline; once an approach is chosen, implement it properly following `production-engineering`.
- For experiments on n08 / n09, follow `lab-gpu-servers` for connecting, picking GPUs, and moving data.

## 1. Before starting: write the exploration plan

Create an exploration plan under `docs/` from the template [`templates/plan.md`](templates/plan.md). Fill in the following before the first experiment:

1. **Problem and invariant contract**: what must not change (interfaces, data formats, numeric precision, test set). If these change, it is no longer the same problem.
2. **A single primary metric**: one number compares every approach, with the conversion formula fixed in writing (e.g. `ms/image = cycles × clock period (ns) / 10^6`). Numbers measured on different bases are not ranked together; when they must appear side by side, label the basis.
3. **Gates**, in three kinds:
   - Quality gate: how correct the result must be (e.g. ΔPSNR ≥ −0.1 dB, bit-exact against the reference);
   - Screening gate: whether it is worth taking to the next level of verification;
   - Final gate: whether it can be declared "feasible". Only approaches that pass the final gate enter the ranking.
4. **Evidence levels**: list your domain's evidence from weakest to strongest, e.g. "paper estimate < local / unit experiment < simulation < synthesis estimate < implementation < hardware measurement". Tag every conclusion with the level it has reached; never present lower-level evidence as higher-level.
5. **Numbering scheme**: series prefixes by direction (e.g. E for baseline and sweeps, P / W / G for individual optimization directions, C for combinations, F for the mainline); IDs are never reused; reserve a separate range for replays (e.g. 100 and above).
6. **Budget and stop rules**: timeout per run; maximum time on any one problem (e.g. 45 minutes), after which you stop and record; concurrency and memory rules for the machines.
7. **Protected artifacts**: baseline source, data, reference outputs. Record their sha256 before starting and verify again at wrap-up.
8. **User decisions**: record them in the plan with dates. When a new decision supersedes an old rule, keep the old rule as history; don't rewrite it.

## 2. Lifecycle of one experiment

| Step | What to do |
|---|---|
| 1. Assign an ID | Confirm it is unused. Completed IDs are never reused; a rerun after a fix also gets a new ID, linked back with a `retry` relation |
| 2. Write and commit the experiment card | [`templates/experiment.json`](templates/experiment.json): purpose, control experiment, **the only thing changed** relative to the control, conditions held fixed, paper estimate and its basis, how it will be judged, and what each possible outcome leads to next. **Commit first, then run** |
| 3. Run in isolation | Copy an independent design or codebase from the control; don't touch files of completed experiments; no concurrent runs in the same working directory; every run has a timeout and a log |
| 4. Archive | `experiments/<id>_<short-name>/`: a copy of the card, raw logs, raw reports, parsed metrics, a one-page note (result, deviation from the estimate, conclusion), plus the source commit and tool versions |
| 5. Register | The registry `results.csv` is appended by the parsing script, never by hand; leave unmeasured values blank, not 0; failures, timeouts, and invalid configurations get a row too |
| 6. Record | Append an entry to `LOG.md`; update the current state in `PROGRESS.md` |
| 7. Commit | One commit per experiment, message starting with the ID, e.g. `F25 nested_weight_loader` |
| 8. Update the evolution graph | Add the node and relations to `graph.json` and regenerate the SVGs (section 6) |

Completed experiments are immutable: to reproduce one, assign a new ID, copy the archived design, and rerun it with the recorded commands.

## 3. When proposing an optimization

1. **Find the bottleneck first, with evidence**: a specific line from a report or profile, e.g. "the 2.822 ns global critical path sits on the 15-bit address multiply in Conv1 weight loading". No experiment is opened on an evidence-free "this should be faster".
2. **State a testable hypothesis**: "Changing X should move the metric from a to b, because …; the likely cost is …".
3. **Pick a control and change only this one thing**: name the control experiment and write the difference in the card's `changes`. Change several factors at once and you can't tell which one mattered.
4. **Commit the paper estimate first**: write the estimate and its basis into the card and commit before running, so it can't be revised after the fact.
5. **Compare the measurement with the estimate**: when they differ a lot, first explain why (where the estimate went wrong), then decide the next step.
6. **Turn the conclusion into a next step**: adopt as the new baseline, keep as a branch, or stop, and say why.
7. **Update the evolution graph**.

Rules of judgment:

- Measure the baseline and fix the numeric contract before optimizing.
- Sweep one parameter dimension at a time, round by round; don't change every parameter at once.
- Local results (a unit, a single layer, a small kernel) don't extrapolate to the whole system.
- Gains from two approaches don't simply add up; a combination must be measured on its own.
- The fastest point that fails a gate stays out of the ranking, e.g. a combination with the lowest latency but three times the LUT budget.
- Failure is a result: keep the node and state the cause. Distinguish "configuration didn't take effect" (invalid: fix and retry) from "valid but below the bar" (a conclusion).
- A tool "exiting successfully" doesn't mean the result is correct; check the actual metrics.
- When one problem hits its budget, stop, record the current state, and switch direction or ask the user.

## 4. File layout

```
docs/NNNN-<topic>.md            exploration plan; conclusions written at wrap-up
exp/configs/<id>.json           experiment cards (committed before running)
experiments/
  PROGRESS.md                   resume entry point: current state, what's running, next steps, how to resume
  LOG.md                        append-only event log
  results.csv                   registry (script-generated)
  graph.json                    evolution graph data: hand-written ideas and relations
  evolution/                    generated .svg / .mmd (don't edit by hand)
  <id>_<short-name>/            per-experiment archive
```

`PROGRESS.md` template: [`templates/PROGRESS.md`](templates/PROGRESS.md).

## 5. Registry and log

**`results.csv`**: one row per experiment, with at least these columns:

`id, time, series, control, changes, status, <primary metric>, <gate-related metrics>, evidence_level, git_commit, archive, notes`

- `status` uses the same values as the evolution graph: `pass / warn / fail / invalid / timeout / planned / analysis / partial`.
- Predictions stay in the experiment card, never in the registry; the registry holds measurements only.
- If a registered result turns out to be wrong, append a correction event to LOG.md and fix it in a new experiment; don't rewrite the original reports and logs.

**`LOG.md`** is append-only, one line per entry, with UTC time and IDs:

```
- 2026-10-10T16:52:16Z: E023/E024/E025 invalid: syn.directive silently ignored by the tool. Now generating directives from the schema and rejecting unknown options; retried as E028/E029/E032.
```

## 6. Experiment evolution graph (SVG directed graph)

The evolution graph answers three questions: **what each experiment builds on, why it was adjusted that way, and how its result led to the next experiment**. Update it when a new optimization direction opens, when a phase wraps up, and when reporting to the user.

**Data**: `experiments/graph.json`. Hand-write a one-line idea for each experiment and where it came from. Example: [`templates/graph.example.json`](templates/graph.example.json); rendered result: [`templates/example-evolution/overview.svg`](templates/example-evolution/overview.svg).

```json
{ "id": "F25", "title": "Disable load-loop flattening", "group": "mainline", "status": "warn",
  "idea": "One change only: LOOP_FLATTEN off", "metric": 2.64, "problem": "Timing warning at 2.5 ns",
  "parents": ["F24"] }
```

**Generate** (requires Node and dagre 0.8.x; see the header of the script):

```bash
node <this skill>/scripts/evolution_graph.cjs experiments/graph.json --all \
     --results experiments/results.csv --metric-column latency_ms
node <this skill>/scripts/evolution_graph.cjs experiments/graph.json --all \
     --results experiments/results.csv --metric-column latency_ms --check
```

`--all` produces the overview `overview.svg` plus one graph per route (`group`); route graphs draw direct sources from outside the route as grey dashed boxes. `--check` writes nothing; it only checks the data rules, node overlap, and whether the generated files are stale.

**Node statuses**:

| status | Meaning | Requirement |
|---|---|---|
| `pass` | Passed the current stage, with a comparable metric | Must have a metric; may add `"selected": true` to mark the current choice (★, bold border) |
| `warn` | Passed with warnings (e.g. timing warnings) | Must have a metric; put the warning in `problem` |
| `fail` | Below the bar, or failed | Must have a one-line `problem`; any metric is shown only in grey |
| `invalid` | Invalid configuration (didn't take effect); faded | Must have `problem` |
| `timeout` | Timed out or interrupted; faded | Must have `problem` |
| `planned` | Planned, not run; dashed border | Must not have a metric |
| `analysis` | Software analysis or numeric study | — |
| `partial` | Local experiment (unit, single layer), no whole-system metric | Don't invent a whole-system metric |

**Relations** (solid lines are design evolution; dashed lines are evidence and verification):

| kind | Meaning | Line |
|---|---|---|
| `source` | Design or parameter baseline (default) | solid |
| `retry` | Retry after a fix | solid |
| `integrate` | Integrates an existing module | solid |
| `reference` | Numeric basis or inspiration | dashed |
| `control` | Control | dashed |
| `verify` | Verification of the same design | dashed |
| `replay` | Reproduction | dashed |

**Drawing rules**:

- Exactly one node per experiment; relations are dependencies between ideas, not Git commit history; no cycles.
- An experiment normally links to one primary source; link several only when integrating, or when bringing in a key numeric basis.
- Keep failed nodes, with a specific one-line problem such as "LUT 248,797, 3× over budget", not just "failed".
- Put only the primary metric on a node; resources, accuracy, and other details go in the experiment record.
- The registry is the source of truth for metrics: cross-check with `--results`, and fix `graph.json` when they disagree.
- Once there are many experiments (dozens or more), split them into routes by `group` and keep only the trunk in the overview; if needed, use route-level summary nodes there.

**Accompanying text**: in the exploration plan or a separate document, write one paragraph per route answering the three questions above, and embed the matching SVG. Readers look at the overview first, then at each route for detail.

## 7. Resuming and handover

- `PROGRESS.md` is the resume entry point: current branch and baseline, completed IDs, running jobs (machine, process, log path), to-dos, user decisions in force, and resume steps. Update it at the end of every experiment.
- Check processes before resuming: remote jobs may have finished or may still be running. For finished jobs, only collect results (collect-only) and don't relaunch them; never start a second copy of a job that is still running.
- The handover document states which conclusions have reached which evidence level, what hasn't been verified yet, and the candidates for the next step with reasons.

## 8. Reporting

Every report uses a table; write `unknown` for anything not measured:

| ID | What changed vs. control | Primary metric | Gate results | Evidence level | Status | Conclusion / next step |
|---|---|---|---|---|---|---|

Also state:

- the currently selected approach, and why it is the one;
- deviations from the paper estimates;
- items that haven't reached the final gate yet;
- the path to the evolution graph.

## 9. Subagents and models

Subagents default to Sonnet; for the setting and the precedence order, see section 7 of `production-engineering`.

- Good fits for Sonnet subagents: running an experiment from its committed experiment card, checking remote jobs and collecting results, parsing reports and appending to the registry, generating and checking the evolution graph, searching past experiments and logs.
- Pass `model: "opus"` explicitly for: finding bottleneck evidence in reports, writing hypotheses and paper estimates, explaining gaps between estimates and measurements, verifying any claim that something passes the final gate.
